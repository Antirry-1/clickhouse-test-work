# DESIGN.md

Обоснование проектных решений для витрины `messages_mart` и дашборда **SMS Operations**.
Сопутствующие файлы: [`README.md`](../README.md) (как запустить) и
[`HUMAN_CHECK.md`](HUMAN_CHECK.md) (проверка простым языком).

---

## 1. Архитектура и поток данных

Диаграммы (Mermaid) — в [`diagrams/architecture.md`](diagrams/architecture.md).

```
generate_data.py ──батчевый HTTP INSERT──▶ ClickHouse: sms.messages_mart (MergeTree)
                                                 │
                                          sms.messages_mart_active  (VIEW, deleted_at IS NULL)
                                                 │
                                   датасет Superset ──▶ 7 чартов ──▶ дашборд «SMS Operations»
```

- **ClickHouse** хранит витрину (одна строка = одно SMS).
- **Вью** `messages_mart_active` отдаёт только не удалённые (soft-delete) строки; датасет Superset
  построен на вью, поэтому каждый аналитический чарт автоматически исключает удалённые строки.
- **Materialized view** `messages_daily_mv` инкрементально наполняет дневной предагрегат
  `messages_daily` (AggregatingMergeTree), чтобы запросы дашборда читали тысячи строк-агрегатов
  вместо 1M — DDL в [`../ddl/002_create_messages_daily_mv.sql`](../ddl/002_create_messages_daily_mv.sql).
- **Superset** подключается по диалекту `clickhousedb://` (драйвер clickhouse-connect) и отдаёт
  дашборд с двумя глобальными фильтрами.
- Витрину делят **два потребителя**: **дашборд** (срезы по клиенту + диапазону времени, группировки)
  и **API-клиенты** (поиск по клиенту / по конкретному сообщению). Физическая модель обслуживает обоих.

## 2. ENGINE — почему `MergeTree`

`MergeTree` — правильный базовый движок для преимущественно append-таблицы аналитических событий:

- Колоночное хранение + разрежённый первичный индекс → быстрые `count()` / `sum()` / группировки,
  а именно это и делает дашборд.
- Одна строка = одно финальное состояние SMS. Обновления (корректировка статуса, soft-delete) редки
  и обрабатываются **в источнике**, поэтому нам **не** нужны семантики дедупликации/схлопывания
  `ReplacingMergeTree` / `CollapsingMergeTree` — а отказ от них сохраняет `count()`/`sum()` точными и
  предсказуемыми (нет «двойного учёта» до фонового слияния).
- Кластерный вариант (`ReplicatedMergeTree` + ClickHouse Keeper, 3 ноды) описан как продакшен-шаг
  (№11) и не нужен для одноузлового воспроизводимого демо.

## 3. `PARTITION BY toYYYYMM(sent_date)` — почему

- Оба потребителя фильтруют по диапазонам `sent_date` → помесячные партиции позволяют ClickHouse
  **отсекать** целые месяцы, которые не нужны запросу.
- Один год ⇒ **12 партиций** (проверено) — достаточно крупно, чтобы число кусков (parts) было
  здоровым, и достаточно мелко для отсечения по месяцам. Партиции по дням дали бы 365 партиций и
  слишком много мелких кусков; партиции по году не отсекали бы ничего полезного.
- Партиционируем по времени **события** (`sent_date`), а не по времени загрузки — это совпадает с
  тем, как данные запрашиваются.

---

## 4. `ORDER BY (customer_id, sent_date, country, delivery_status, message_id)` — ключевой компромисс

Это самое важное решение, потому что **у витрины два потребителя** (в задании об этом прямо
предупреждают):

| Потребитель | Типичный запрос | Чем обслуживается |
|---|---|---|
| Дашборд Superset | фильтр `customer_id` (глобальный) + диапазон `sent_date` (глобальный), затем группировки по дню / стране / статусу / оператору | ведущий префикс `(customer_id, sent_date, ...)` |
| API-клиенты | сообщения клиента / приложения за период; поиск одного `message_id` | ведущий префикс (клиент + время) + **skip-индексы** для одиночных id |

Рассуждение по колонкам:

1. **`customer_id` первым** — самая низкая кардинальность (8 клиентов), и по нему фильтруют *все*
   запросы дашборда и большинство API-запросов. Первое место делает доступ по клиенту дешёвым
   непрерывным сканом и даёт лучшее отсечение по первичному индексу.
2. **`sent_date` вторым** — оба потребителя фильтруют по времени; внутри клиента данные отсортированы
   по времени, поэтому диапазонные сканы непрерывны и согласованы с помесячным партиционированием.
3. **`country`, `delivery_status`** — улучшают локальность данных для чартов «топ стран» и «по
   статусам» (строки одной страны/статуса лежат рядом → затрагивается меньше гранул).
4. **`message_id` последним** — высококардинальный «добивающий» столбец, делающий ключ сортировки
   **уникальным**, чтобы куски сливались чисто, а порядок был детерминированным.

**`PRIMARY KEY (customer_id, sent_date)` ≠ `ORDER BY`.** Первичный ключ намеренно короче ключа
сортировки. Данные физически отсортированы по полному `ORDER BY`, но разрежённому первичному
**индексу** достаточно `(customer_id, sent_date)` — тех колонок, по которым реально фильтруют. Это
держит индекс в памяти маленьким, сохраняя при этом полную локальность сортировки. (ClickHouse
разрешает первичному ключу быть префиксом ключа сортировки именно для такой оптимизации.)

**Nullable-ключи.** `country` и `delivery_status` — это `LowCardinality(Nullable(String))` по
спецификации, и они входят в `ORDER BY`, поэтому в таблице задан `allow_nullable_key = 1` (NULL'ы
сортируются первыми). Это реальная ошибка, всплывшая при сборке (без настройки DDL не применялся), и
ровно та «будьте внимательны с ключами сортировки» дилемма, на которую намекает задание.

### Чего ключ сортировки **не** обслуживает → skip-индексы (№5)
Поиск одиночного `message_id` (или `application_uuid`) без `customer_id`/времени **не** является
префиксом ключа сортировки, поэтому первичный индекс его не отсечёт. Это паттерн point-lookup'а API,
и он решается skip-индексами, а не раздуванием ключа сортировки.

## 5. Skip-индексы — только там, где они оправданы

```sql
INDEX idx_message_id       message_id       TYPE bloom_filter(0.01) GRANULARITY 1,
INDEX idx_application_uuid  application_uuid TYPE bloom_filter(0.01) GRANULARITY 1
```

- **Почему именно эти два:** API-клиенты ищут по `message_id` (id вендора) и `application_uuid`
  (срезы по приложению). Ни один из них не является эффективным префиксом ключа сортировки.
  Bloom-фильтр позволяет ClickHouse пропускать гранулы, которые точно не содержат значение.
- **Доказано, а не «для галочки».** `EXPLAIN indexes=1` для поиска по `message_id`:
  `idx_message_id` сократил скан с **154 → 4 гранул** (и 59 → 4 кусков).
- **Почему больше ничего:** `country` / `delivery_status` / `receiver_operator` и так
  низкокардинальны и хорошо обслуживаются ключом сортировки + `LowCardinality` — лишний индекс лишь
  добавил бы стоимость записи/слияния без выгоды на чтении. (Сознательный отказ от переусложнения.)

### Замечание о типе `receiver`
`receiver` имеет тип `LowCardinality(Nullable(String))`, потому что так предписано спецификацией, хотя
настоящий MSISDN высококардинален (плохо подходит под `LowCardinality`). Генератор берёт получателей
из ограниченного пула по стране (~98k уникальных — реальный трафик повторно идёт к тем же абонентам),
что держит словарь вменяемым. **В проде** я бы хранил `receiver` как обычный `String` (или разбивал на
префикс страны + номер абонента), а не `LowCardinality`.

## 6. Soft delete — `deleted_at IS NULL`

- Аналитические запросы должны игнорировать удалённые (soft-delete) строки. Вместо того чтобы
  полагаться на то, что автор каждого чарта вспомнит про `WHERE deleted_at IS NULL`, датасет построен
  на **`messages_mart_active AS SELECT * FROM messages_mart WHERE deleted_at IS NULL`**.
- Каждый чарт дашборда наследует фильтр → корректность **по построению**.
- **DQ / владелец данных** может читать **базовую таблицу**, чтобы видеть удалённые или аномальные
  строки (см. №10).

## 7. Дашборд — метрики и фильтры

> Готовый, копипастящийся SQL по всем 13 графикам и 6 метрикам — в
> [`dql/dashboard_queries.sql`](../dql/dashboard_queries.sql) (пояснение — [`dql/README.md`](../dql/README.md)).

### Глобальные фильтры (native)
| Фильтр | Поле | Тип |
|---|---|---|
| **Customer** | `customer_id` | мультивыбор |
| **Sent date** | `sent_date` | диапазон времени |

Оба видны в левой панели на скриншоте. Фильтр клиента прокидывает `extraFormData`-предикат в каждый
чарт; фильтр диапазона времени ограничивает временную колонку.

### Обязательные чарты
| Чарт | Тип | Логика |
|---|---|---|
| SMS по дням | Time series (линия) | `count(message_id)` по дню `sent_date` |
| Delivery rate | Big Number | `round(100 * avg(delivery_status = 'DELIVRD'), 2)` |
| Топ стран | Bar | `count(message_id)` по `country`, топ-10 |
| Топ операторов | Pie | `count(message_id)` по `receiver_operator`, топ-10 |
| Выручка (всего) | Big Number | `sum(price)` |

### Дополнительные чарты (на усмотрение кандидата)
| Чарт | Тип | Логика |
|---|---|---|
| Выручка по валютам | Bar | `sum(price)` с группировкой по `currency` |
| Failed statuses | Bar | `count(message_id)` по `delivery_status`, где `delivery_status <> 'DELIVRD'` |

### Тарифицируемые / доставленные статусы
Доставленным/тарифицируемым в этой модели считается только **`DELIVRD`**. Всё остальное
(`UNDELIV, EXPIRED, NO ROUTES, SENT, ROUTE FAILED, REJECTD, VND CHN NOT BND,
SUBMIT_RESP TIMEOUT, UNKNOWN`) — «не доставлено» и попадает в чарт «Failed statuses».

### Delivery rate (доля доставки)
`100 * (число DELIVRD) / (число всех активных строк)` — считается по `messages_mart_active`
(soft-delete исключён). Проверено ≈ **80.03%**.

### Выручка (revenue)
`sum(price)`, где `price` — в валюте `currency` строки. **Валюты не приводятся по курсу (без FX)**:
Big Number «Выручка (всего)» суммирует цены по смешанным валютам (это сознательное, явно описанное
упрощение — в подзаголовке написано «mixed currency»), а **«Выручка по валютам»** разбивает её по
`EUR / RUB / USD`, чтобы микс был виден. В проде настоящий KPI выручки приводил бы всё к одной валюте
отчётности через таблицу курсов с джойном по `sent_date`.

## 8. Как фильтры доходят до чартов
- У датасета `main_dttm_col = sent_date` → временные фильтры применяются ко всем чартам; не-временные
  чарты задают `granularity_sqla = sent_date`, чтобы фильтр диапазона времени ограничивал и их.
- Native-фильтр клиента нацелен на `messages_mart_active.customer_id`; так как все чарты на одном
  датасете, выбор клиентов перезапрашивает каждый чарт.

## 9. Допущения при генерации данных
- **Фиксированный год**: `2025-01-01 .. 2026-01-01` (совпадает с `data_spec.json`). Объём по умолчанию 1 000 000.
- **Воспроизводимость**: сид RNG (`--seed 42`); UUID приложений детерминированы (`uuid5`).
- **8 клиентов**, у каждого **1–4** application UUID (15 всего в сид-прогоне); часть клиентов шлёт
  заметно больше остальных.
- **CIS-взвешенный** микс стран (Россия ≈ 41%), с мэппингами страна→оператор и страна→телефонный префикс
  для реалистичности.
- **Микс статусов** ≈ 80% `DELIVRD` с реалистичным «хвостом» ошибок; `delivery_time` коррелирует с
  исходом (доставка быстрее, ошибки медленнее); `segment_count` смещён к 1–2; `attempt_number` смещён к 1.
- **Валюта** с перевесом RUB (≈55%); `price` = базовая ставка по стране × сегменты × шум, обрезано в
  диапазон спецификации `[0, 1]`.
- **Soft delete**: ≈1.5% строк имеют `deleted_at`.
- **Настоящие NULL** добавлены (~0.4–1%) в `sender / country / currency / receiver_operator` (отдельно
  от sentinel-значения `not_defined`), чтобы вью soft-delete и DQ-дашборд имели смысл.
- **Самопроверка**: по завершении генератор печатает сводку (число строк, период, доля `DELIVRD`,
  объём soft-delete, распределение по валютам), так что результат виден прямо в логах
  `make generate` — без отдельных ручных запросов.

## 10. Что реализовано из «можно/было бы круто»
- **Доп. фильтры** доступны на датасете: `country`, `delivery_status`, `currency`.
- Чарт **«Выручка по валютам»**.
- **Failed statuses**, **направление (inbound/outbound)**, **delivery_time**, **segment_count** —
  всё это колонки, готовые для доп. чартов; **DQ-дашборд** можно собрать на **базовой таблице** и
  показывать: долю NULL по колонкам, объём soft-delete, доли `not_defined`, выбросы по delivery_time.

## 11. Что улучшить для продакшена
- **Кластер**: `ReplicatedMergeTree` + ClickHouse Keeper (3 ноды), DDL `ON CLUSTER`, таблица
  `Distributed` для разлёта запросов. Текущий DDL написан так, что переход механический.
- **`receiver`**: использовать `String` (или разбиение на префикс/номер) вместо `LowCardinality`
  под реальную кардинальность MSISDN.
- **Выручка**: приведение по курсу (FX) через измерение курсов валют с джойном по `sent_date`.
- **Секреты**: настоящий менеджмент секретов (без дефолтных паролей), TLS, CH-пользователи с
  минимальными правами.
- **Superset**: метаданные в Postgres + Redis + Celery (асинхронные запросы, алерты, превью),
  включить обратно CSRF/Talisman, RBAC, row-level security по клиенту.
- **Загрузка**: заменить генератор на реальный пайплайн сборки из нескольких потоков; добавить
  контракты данных и DQ-тесты (например, dbt / Soda) на витрину.
